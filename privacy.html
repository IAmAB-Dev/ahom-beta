Privacy statement

Ahom is a desktop mail client that runs entirely on your device. There is no Ahom server, no Ahom account, and no Ahom backend in the data path — so most of this document is about the things Ahom deliberately does not do.

The short version

Ahom collects nothing about you. Your mail is stored, encrypted, on your own machine. AI features run on your device. Nothing is sent to Ahom, because there is no Ahom server to send it to. If a section below sounds short, it is short on purpose — the substance is “Ahom does not do that thing.”

What changed in 1.10

Two tightenings of the same boundary — data leaving the device without a clear local approval. A shared-drafts relay that is not on this machine now needs its own “Allow remote relay” opt-in, even when the relay address arrived inside an invite. And the “is this local?” check behind that switch and behind “Allow remote AI” got stricter: only localhost, 127.0.0.0/8 and ::1 count as this device; .local / .lan names and link-local addresses no longer do. Nothing makes more data leave the device by default — if anything, less does.

What Ahom collects

Ahom collects nothing about you. There is no telemetry, no analytics, no crash reporting, no usage metrics, no install pings, and no remote configuration service. The binary you install does not phone home.

The app reads, writes, displays, indexes, and stores mail on your device, on your behalf, using credentials you supply. None of that data is transmitted to any infrastructure operated by Ahom or Plenith LLC, because no such infrastructure exists.

Where your data lives

Everything stays on the device where Ahom is installed:

  • Mail content (headers, bodies, attachments, drafts, search index) is stored in a single database file in your application-data directory, encrypted at rest with SQLCipher using AES-256. The encryption key is generated on first launch and sealed in the operating-system keychain — Windows Credential Manager, macOS Keychain, or libsecret on Linux. The key never lands on disk in plaintext.
  • Attachments live inside that same encrypted database — no separate plaintext blob directory on disk, so a stolen disk image yields zero plaintext attachment bytes. Attachment bytes are fetched on demand from your provider only when you open or save a file; they are never pre-downloaded for offline use.
  • OAuth refresh tokens for Gmail and Microsoft accounts are sealed in the same OS keychain. Plain IMAP / SMTP passwords, when you use them, are also stored in the keychain — never in the database, never in a config file.
  • PGP private keys are double-protected: passphrase-wrapped using OpenPGP S2K (you set the passphrase at key generation), then stored inside the encrypted database. Compromising one layer alone does not yield the key.
  • UI preferences (theme, density, sidebar width) live in browser-side local storage and contain no mail content.
  • Local-AI model files live in a models/ subdirectory of the application-data directory — next to the mail database, not in the install directory. They are downloaded once, verified against a pinned SHA-256, and contain no prompts, responses, or mail content.

Uninstalling the app and deleting the application-data directory removes every byte of mail content the app has ever stored, and the model files with it — one step, nothing left behind.

How information is used

Information is used to operate the app on your behalf: rendering the inbox, opening threads, running search, generating thread summaries, drafting replies, classifying mail into buckets, and sending what you compose. Every one of those operations runs on your device against the local database.

Local AI features (summary, draft, natural-language search, smart-inbox classification) run against a language model on your own machine. The app’s Engine setting controls which runtime serves them:

  • Embedded (default) — the model is loaded inside the app’s own process and runs inline. There is no HTTP listener on this path: no socket the OS, another process, or a port scanner could observe. No prompt, message, or response leaves the device.
  • External — you pin the app to your own local runtime (LM Studio, Ollama, or another OpenAI-compatible endpoint). Pointing it at a non-loopback URL is the only setting that causes AI payloads to leave the device: it needs the separate “Allow remote AI” opt-in, and a per-feature badge surfaces it before any call. “On this device” means exactly localhost, 127.0.0.0/8 or ::1 — a .local / .lan hostname or a link-local address names some machine on your network, not necessarily this one, so those count as remote.

In every case other than a non-loopback External URL, AI traffic stays on the device — either as in-process function calls or as loopback HTTP to a local runtime on your own machine.

Data sharing

Ahom does not share your data with anyone, because Ahom does not have your data. The app communicates with a small set of endpoints, all controlled or chosen by you:

  1. Mail providers you connected — Gmail, Microsoft Graph, and the IMAP / SMTP servers you configured. Traffic on this path is what every mail client sends: authenticated API and mail-protocol sessions over TLS.
  2. A local AI endpoint (External engine only) — HTTP calls to whatever base URL you configured, loopback by default. The Embedded engine uses no HTTP at all. The default configuration sends nothing.
  3. Model downloads — the local chat model, and the optional semantic-search embedding model, are fetched once from a public model host as ordinary anonymous HTTPS downloads, each pinned to a SHA-256 the app verifies. Neither request carries an account, an identifier, information about you, or anything about your mail.
  4. A shared-drafts relay (optional) — if you use real-time draft collaboration, change data is end-to-end encrypted (AES-256-GCM) under a key the relay never sees; the relay only routes ciphertext. The app connects to a relay automatically only when it resolves to this machine (localhost, 127.0.0.0/8, ::1). Any other relay — including one named inside a workspace invite someone sent you — needs the “Allow remote relay” switch in Settings → Collaboration, which is off by default; until you turn it on, a shared draft pointed at a remote relay simply shows as offline. There is no Ahom-operated relay — you self-host or trust one you choose, and the default install has none.
  5. Verified sender logos (BIMI), when enabled — for a sender whose message passed authentication, the app fetches that organization’s published logo from the organization’s own server, never through any third-party aggregator. See below.

There are no advertising networks, no third-party SDKs, no fingerprinters, no identifiers, and no marketing pixels in the app.

Provider data flows & OAuth scopes

When you connect an account, mail data flows directly between your device and the provider — never through Ahom.

  • Gmail. OAuth 2.0 with PKCE on a loopback redirect. Scopes requested: https://www.googleapis.com/auth/gmail.readonly (list and read messages and threads) and https://www.googleapis.com/auth/gmail.send (send mail you compose in the app). Ahom requests no scope that would let it delete your mail or change your account settings. The refresh token is sealed in the OS keychain and used only to talk to Google from your device. Ahom does not transfer Google user data to any server, does not use it for advertising, and does not use it to train any model.
  • Microsoft 365 / Outlook. OAuth 2.0 against the common tenant. Scopes requested up front: Mail.Read, Mail.ReadWrite (move messages between folders for triage), Mail.Send, User.Read (resolve the signed-in mailbox identity), and offline_access (issue a refresh token). All are presented on Microsoft’s consent screen when you first connect. The refresh token rotates on every refresh and is sealed in the OS keychain.
  • iCloud, Fastmail, Yahoo, and generic IMAP / SMTP. Credentials you provide (typically an app-specific password for iCloud and Yahoo) are sealed in the OS keychain. The app talks IMAP and SMTP directly to the host you configured, over TLS via the system trust roots.

Your use of each provider is governed by that provider’s own privacy policy. You control how much mail is fetched: sync can be bounded by count and by recency, and those bounds only ever reduce what the app requests from a provider.

Cookies and tracking

Ahom is a native desktop application, not a website. There are no cookies and no tracking pixels in the app’s own interface. Remote images in inbound mail are blocked by default to defeat third-party tracking pixels, and known-tracker beacons are stripped at the sanitize layer even when you choose to load images for a specific message.

Verified sender logos (BIMI)

BIMI (Brand Indicators for Message Identification) lets an organization publish a logo, tied to email authentication, so genuine mail can display its brand mark. Ahom supports it so that a real message from, say, your bank can show the bank’s verified logo — a positive authenticity signal you can see at a glance. Because it makes a new kind of network request, here is exactly how it is minimized:

  • Authentication gate. A logo is only ever fetched or shown for a message that passed DMARC. Unauthenticated, failing, or phishing/untrusted mail never shows a logo — it shows sender initials.
  • Fetched at sync time, not on open. The logo is resolved in the background when mail is synced, once per sender domain — never when you open or read a message. The request therefore never reveals which message you read or when.
  • Cached locally, brand’s own server only. The logo is stored in your encrypted database and reused; the fetch is HTTPS-only, size- and time-limited, follows no redirects, and comes only from the address the sending domain publishes in its own DNS. Ahom never uses a third-party “logo for any domain” service.
  • A real setting. “Show verified sender logos” (Settings → Appearance) defaults on; turning it off stops every logo fetch and shows initials instead.

What never leaves your device for this feature: your mail, subjects, contacts, account identity, and which messages you open. The only thing a brand’s server can infer is that some account received authenticated mail from their domain — which they already knew, because they sent it.

Security measures

  • At rest: SQLCipher with AES-256 wraps the entire mail database; the master key is sealed in the OS keychain.
  • Credentials: OAuth refresh tokens, IMAP / SMTP passwords, and the database master key all live in the OS keychain.
  • PGP private keys: double-encrypted — passphrase-wrapped via OpenPGP S2K before the database sees them.
  • End-to-end: when both you and your correspondent have OpenPGP keys, mail can be encrypted before it leaves your device; the provider only sees armored ciphertext.
  • In transit: TLS via the operating-system trust roots for all provider traffic.
  • Rendering: inbound HTML is sanitized in Rust before display, then rendered inside a sandboxed frame with no script execution.

Ahom cannot defend against every threat. A compromised operating system can read decrypted mail and unlocked keys from process memory while the app is running, and a breach at your mail provider exposes anything the provider stores unencrypted.

Your rights and controls

Because Ahom holds nothing about you on infrastructure it controls, the usual “request a copy of my data / delete my data” workflow does not apply — there is nothing on the Ahom side to retrieve or erase. What you control on your own device:

  • Export / back up. Export writes a copy of your mail to a standard .mbox file at a location you choose — a portable backup you own, importable into other mail clients. It is a local file write you initiate; nothing leaves your device.
  • Clear local caches. Clear derived caches (AI summaries, the search index, meaning-search vectors, fetched sender logos) individually or all at once. Each is regenerated from mail already on your device, so clearing is safe.
  • Disconnect an account. Wipes that account’s credentials from the keychain; a per-account “remove data” also deletes that account’s cached mail.
  • Delete everything. Uninstall the app and remove the application-data directory. That deletes every byte of mail and every credential Ahom has ever held.

For the data your provider holds, use the provider’s own privacy controls — that data is governed by them, not by Ahom.

Logs

Ahom writes a small amount of operational information to standard error during normal operation: performance markers, authentication-flow milestones, error messages from the OS or your mail providers, and counts. On a normal install this stream is not redirected to a file — the logs vanish when the app exits.

It does not log token contents, mail bodies, mail subjects, attachment payloads, PGP keys, passphrases, or recipient addresses. Diagnostic lines that would touch any of those are gated behind opt-in environment variables that are off by default, including in shipping release builds.

Update payloads are signed at build time and verified on your device against a public key shipped with the app, so an update that was not produced by our release pipeline is rejected before it is applied. No shipped build polls for updates in the background.

International users and GDPR

Ahom does not act as a controller or processor of personal data under the GDPR, because it does not collect, store, transmit, or otherwise process personal data on infrastructure it controls. The mail providers you connect are independent controllers for the data they hold. If you are subject to data-residency rules, mail content lives wherever your device lives — there are no cross-border transfers initiated by Ahom itself.

Children

Ahom is not directed at children under 13 (under 16 where that is the threshold) and does not knowingly collect information from children, because it does not knowingly collect information from anyone. If you are under the relevant age in your jurisdiction, do not use the app.
